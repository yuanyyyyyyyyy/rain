## 一、云枢智慧医院管理平台（→ zero-one-his2607 的 agent）

用途：首页旗舰卡 + 项目详情页 001（全站最重要的 case study）。

### P0 必须提供

1. **时间线确认**：项目起止时间是否为 2026.05 — 08？
2. **微服务架构清单**（用于绘制工业线条风格架构图）：
   - 有哪些服务（服务名 + 一句话职责）；
   - 网关 / 注册中心 / 配置中心（Nacos）的接入方式；
   - 排班预约服务与其他服务之间的调用关系（谁调谁、同步还是 MQ）。
3. **我的职责边界**：独立负责排班预约服务的准确范围（日/周排班模板、号源管理、停诊管理、停诊通知、REST API）。确认 API 数量是否为 18 个，列出代表性接口名。
4. **核心实现逐条说明**（每条按"问题/动机 → 方案 → 效果"三段，各 2—4 句）：
   - Redis Cache-Aside：缓存了什么数据、空值缓存与随机 TTL 的具体参数、一致性如何处理（先更库后删缓存？延迟双删？）；
   - 乐观锁 @Version：用在哪个业务冲突场景（例：同一号源并发预约？）；
   - Redisson 锁 + 双重检查：锁的 key 是什么、防的是什么场景；
   - N+1 → IN 批量查询 + 内存组装：原查询长什么样、改后长什么样；
   - RocketMQ 停诊通知：生产者/消费者在哪个服务、唯一索引幂等的表和字段、重试与死信队列的配置；
   - EXPLAIN 优化：一个具体 SQL 优化案例（优化前后的执行计划关键差异）。
5. **性能测试说明**：
   - 工具（JMeter？）与环境（本机 / 虚机配置）；
   - 测试的接口和场景；
   - 50 并发 / 2000 请求下：平均响应 99.3ms → 19.7ms、吞吐 496 → 2480 req/s、P99 1.47s → 0.15s——确认这组数字及"优化前"的定义（优化前是没加缓存？还是首次压测基线？）；
   - 优化动作清单（哪些改动贡献了提升）。
6. **AI 排班助手**：
   - Spring AI / ChatClient / Function Calling / RAG 各自在链路里的位置；
   - 意图识别 → 调度规划 → API 调用 的完整流程；
   - "合规判定由确定性规则引擎负责"的具体实现（规则引擎是什么形态：硬编码校验类？配置表？）；
   - 排班规则文档 RAG 检索的实现（文档切分、向量库、Top-K）。

### P1 增强（有则更好）

7. **踩坑 2—3 个**：现象 → 排查过程 → 根因 → 解决 → 验证（这是详情页"05 问题与解决"的核心素材，越具体越好）。
