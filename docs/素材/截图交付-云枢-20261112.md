## 4. 审计发现 —— 图注定稿前建议先看

截图制作前对 v1 / 主仓库代码做了一轮审计，发现并处理了以下问题。**其中 3 个真实 bug 是本次修复后才截到图**，图注措辞已按修复后的真实行为撰写：

1. **P1 · 前端周排班保存不回传 `version`，乐观锁在 UI 链路上失效（已修复）**。修复前：保存 payload 不含 version 字段，MyBatis-Plus 对 null version 跳过版本条件 → 并发覆盖照常发生（实测：版本被改后保存仍返回"已保存"）。修复内容见 §6 复现指引。修复后实测：旧版本提交被 0 行更新拒绝 → Y2 红色报错即此证据。**口径提示**：报错文案"周排班模板不存在或已删除"是后端对"不存在/编码重复/版本冲突"三种失败的统一文案，不区分冲突原因；如需"版本冲突"字样需后端把 0 行更新单独分支（未改，避免为截图改语义）。简历如写"乐观锁防并发覆盖"，以本截图 + 代码为准是成立的，但**面试别把这句报错说成"提示版本冲突"**。
2. **P1 · 单日停诊例外按月查看时整体消失（已修复）**。`BkgCalendarExceptionServiceImpl.queryCalendarExceptions` 用 `le(range_end, 窗口结束)` 过滤，单日例外 `range_end` 为 NULL 时比较恒假 → 11 月视图里 11-16 停诊"不存在"（无过滤时能查到 2 条，带月份过滤变 0 条）。已改为生效区间 `[exception_date, range_end ?? exception_date]` 与查询窗口求交集，重编译部署后 Y3 即修复后的真实输出。
3. **P2 · `loginContext` 覆写丢失 `organizationId`（已修复）**。`stores/user.ts` 的 `setLoginContext` 只持久化 tenant/hospital/department 三键，而排班设置页只读 `organizationId` → 页面永远"未选择机构"。已补 organizationId 的保留与回传。
4. **P2 · his-j8-clinics 未提交改动的撤销停诊疑似 bug（未修复，仅记录）**。主仓库把清空替诊信息从 `LambdaUpdateWrapper.set(null)` 改成 `updateById(entity 置 null)`——MP 默认 NOT_NULL 策略会**跳过 null 字段**，替诊人/原因清不掉；且 v1 里的"恢复号源状态"逻辑在该版本中被删除。运行时用的是 v1 jar 不受影响，但这批未提交代码合并前需要处理。
5. **P3 · `bkg_doctor_profile` 表缺失**。AI 调度助手（PLAN 分支的医生名册/冲突体检/替补推荐）依赖该表，但库里没有 → 调度助手运行时会失败。已按实体字段重建表 + 补 20 名演示医生（张三/李四/王五/赵敏/刘洋…，含 2 个休假区间样例）。注意调度助手目前**没有对应 REST 接口**，仅 AI 工具可用。
6. **P3 · 停诊区间收窄时旧任务不回收**。MQ 消费者只在 CANCELLED 时作废通知任务，UPDATED 事件只做幂等插入：把 11-16~11-20 缩到 11-16 后，11-17~11-20 的 PENDING 任务会残留。
7. **口径差 · "JPA 分页" vs 实际**：需求文案要点里写"JPA 分页"，实际是 **MyBatis-Plus 分页插件**（Page/Pageable 风格的接口设计）。Y1 图注按实际写的是"条件分页 + orgId 多租户过滤"，没提 JPA；网站侧 summary/impl 节如有 JPA 表述建议一并核对（学习材料里"JPA 风格"的口径指接口形态，不是底层实现）。
8. **口径核实 ✓**：25 接口（24 REST + 1 AI）与 Y5 侧栏计数完全一致；"24 REST + 1 AI 接口"的表述可放心用。
