## 四、问题 3 · AI 链路（上传 → 处理 → 生成，及失败降级）

**正常链路**：
1. 前端上传 → `POST /api/upload`（Multer 内存存储）→ Sharp 生成压缩图 + 缩略图 + 提取 EXIF → 上传 R2 → 返回 url/thumbnailUrl/EXIF（upload.js:106-140）。
2. 前端携带元信息调 `POST /api/photos` 建档；**若标题/心情为空 → 自动调 `generatePhotoMetadata(url, …)`**（photos.js:421-435）。
3. `generatePhotoMetadata`：按用户加载 AI 配置（ai_settings 活跃预设 → 回退 .env 默认，ai.js:23-71）→ Ollama 走原生 `/api/chat`（图片转 base64，ai.js:523-556）/ 智谱等走 OpenAI 兼容 `/chat/completions`（ai.js:584-599）→ 提示词要求"仅返回 JSON{title, mood, tags}"（ai.js:492-512）。
4. 解析层 `safeParseJSON`：剥离 markdown 代码块 → 提取首尾大括号 → JSON 失败再兜底解析中文自然语言（`标题：/心情：/标签：`，支持编号列表与分隔符，ai.js:77-117）→ 标签去重后写入 `tags` + `photo_tags`（事务，photos.js:437-466）。
5. 其他 AI 能力同层复用：故事摘要（storyline.js:231）、年度回顾（review.js）、分享文案（4 种风格模板）、搜索词改写（5s 超时 + 缓存）、猫咪对话（人格 system prompt + SSE 流式）。

**异常降级（逐条有代码出处）**：
- AI 未启用/未配置 → `generatePhotoMetadata` 直接返回空值，照片仍正常入库（无标题），**上传链路永不因 AI 失败而中断**（ai.js:482-489、photos.js:432-434）。
- Ollama 拒绝多图分析 → 正则识别拒绝话术（`无法分析|don't have the capability` 等）→ **自动降级为单图重试**（ai.js:541-567）。
- AI 调用失败 → catch 后返回空 metadata；猫咪对话返回"喵……小猫现在有点累了"兜底文案（ai.js:281-283）；搜索 AI 5 秒超时直接走原始关键词（ai.js:744-751）。
- 年度回顾错误分类：INVALID_API_KEY / INVALID_MODEL / TIMEOUT / NETWORK_ERROR / RATE_LIMIT，分别映射用户可读提示（ai.js:671-692）。
- 流式读取 60 秒无数据自动断开（ai.js:298-309）。

**实况验证**：本次审计在本机用 Ollama qwen3:4b 走 `/api/ai/chat/stream` 完成了一次真实流式对话（截图 shimmer-05），AI 链路真实可用；视觉模型 llava:7b 在 6GB 显存机器上 CUDA OOM 无法加载（llama-server 启动报错），故视觉元数据生成未能在本机实况演示——已有数据中存在其历史生成结果（如照片 33 的英文标题 "A serene lake scene with a traditional Japanese boat" 与 Lake view / Japanese art 等标签，为当时 AI 生成后入库）。

## 六、问题 5 · 可写进"问题与解决"的真实踩坑

**坑 1 · Ollama 视觉模型拒绝多图输入（有完整修复代码）**
- 现象：多张照片一起发给 llava 时，模型回复"无法分析多张图片"类话术，元数据生成直接失败。
- 解决：`ollamaRejectPattern` 正则识别拒绝话术（含中英文 6 种模式）→ 命中后**自动降级为仅带第一张图重试**（services/ai.js:541-567）。
- 出处：commit `d51a419 fix: Ollama多图拒绝时降级单图重试`。

**坑 2 · AI 流式对话经 Vite 代理卡顿（SSE 被缓冲）**
- 现象：猫咪对话的流式输出不逐字出现，整段卡住后一次性吐出。
- 排查：SSE 响应被 Vite 开发代理缓冲。
- 解决：vite.config.js 代理对 `/chat/stream` 特判，设置 `cache-control: no-cache` 与 `x-accel-buffering: no` 立即刷新（vite.config.js:13-22，注释原话"关键修复：禁用流式响应的缓冲，解决 SSE 传输卡顿问题"）；后端流式读取另加 60 秒空闲超时防悬挂（services/ai.js:298-309）。
- 出处：vite.config.js 注释 + ai.js 流式实现。

**坑 3 ·（本次审计新发现，建议修复后再上线）故事摘要跨用户串显**
- 实测：用户 `123` 的"gris"故事线（2026-02）显示了**另一个用户**照片生成的春节摘要（"春节的黄昏，我蹲在外婆家…"）。
- 根因：`story_summaries` 表以 `story_date`（月）为**全局唯一键**、无 `user_id` 字段（DESCRIBE 实测：`story_date varchar(10) NO UNI`），而故事线按"用户自己的照片"聚合 —— A 用户先生成的摘要会被 B 用户同月的分组 LEFT JOIN 命中（storyline.js:95）。
- 影响面：跨用户内容泄露（本次截图已避开该分组）。
- 修复建议：摘要键改为 `user_id + story_date`，或查询时校验该月照片归属后再返回缓存。
