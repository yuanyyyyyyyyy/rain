## 一、开工前必做（每次恢复会话的第一步）

```bash
git fetch origin
git status -sb
git log --oneline -3 origin/main
git merge-base --is-ancestor origin/main HEAD && echo BASE_OK
```

打印 `BASE_OK` 才说明本地基于同一基线，可以继续开发 / 发布。
**没打印** = 本地落后或分叉：先别 commit、别 push、别点管理台「04 发布」，找仓库主人对齐后再动手。

`git status -sb` 应显示 `## main...origin/main`；若没有 upstream，
先执行 `git branch --set-upstream-to=origin/main main`。

## 二、禁止

- `git push --force` / 自行 `git reset --hard` 丢弃本地提交（会覆盖另一会话的成果）。
- 运行 `tools/sync-via-api.py` 做全量历史重放（脚本已加护栏，找不到可信断点会直接退出）。
- 还原 `tools/sync-via-api.py` 与 `.github/workflows/deploy.yml` 里的并发护栏。
- `git checkout .` / `git clean`（工作区可能有未提交改动与 `docs/素材/` 下的用户素材）。
- 两个管理台同时发布；发布是单点操作，一次只跑一个。

## 三、发布链路的分工（最容易踩的坑）

- 管理台「04 发布」只 commit `src/data` + `public/photos` + `public/screenshots`，
  然后 `git push origin HEAD:main` → GitHub Actions 构建部署（约 1 分钟）。
- **页面组件、样式、加载逻辑、后端代码不在发布范围内**，必须显式 `git push`
  触发 Actions 才会在公开站点生效。只点发布 = 代码改动永远不上线。
- `PublishService.commitAndSync()` 推送前会 `git fetch` 并校验
  `merge-base --is-ancestor origin/main HEAD`；分叉时发布标记 **FAILED** 并把原因返回管理台，
  不再回退全量重放。只有基线一致且 push 因网络失败时，才允许 API 续传兜底
  （脚本 v3 会再做 message + tree 双匹配校验）。
- Actions 的 `Guard against stale tree` 会在 build 前检查摄影页 `48vw`、
  详情页 `shotThumb` 标记；仓库被回退成旧树时部署直接失败报警，不会把旧版发到线上。

## 四、分叉了怎么办

1. `git fetch origin && git log --oneline -3 origin/main`，先看清对方改了什么。
2. `git diff --name-status origin/main HEAD` 列出两边差异，**逐文件判断哪边是新版**，
   不要整棵树覆盖。
3. 优先 `git pull --rebase origin main`（只搬自己的提交，不重写对方历史）。
4. 若树被大范围回退成旧版：用独立工作树基于 `origin/main`，以完整树为准、
   只保留对方的有效改动，生成一个**快进**提交；禁止 force push。
5. 对齐后所有端 `git fetch` 到同一 HEAD 再继续。
